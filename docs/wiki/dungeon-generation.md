# 副本生成管道（Dungeon Generation Pipeline）

---

## 核心哲学

副本生成与工坊合成共享同一架构原则：**机制与内容彻底分离**。整个管道的 prompt 模板不包含任何世界观相关的故事内容——副本主题、生态底色、场景氛围、生物特征全部通过系统消息注入。换一套战役设定与角色规范，管道代码无需任何修改。

→ 参见：[工坊合成管道（Craft Pipeline）](craft-pipeline.md)

---

## 为何是接力管道而非单步调用

副本涉及三层创作——整体前提、逐个场景、每个场景的怪物——且后一层依赖前一层的产出。因此设计为四步 `ReactiveProcessor` 接力：每步完成时写入中间 JSON 并替换实体上的 Action 组件，触发下一步。中间文件落盘使任意步骤失败后可从断点恢复，无需重跑全链路。

---

## 四步分工与设计意图

**Step 1 — 前提设定**。一次 LLM 调用锁定副本名称、前提描述与场景数量。前提刻意回避角色身份与评价性词汇，只呈现感官与情境细节，为后续留出创作空间。

**Step 2 — 场景设计**。在 Step 1 的同一 agent 上下文内一次性生成全部战斗场景。一次调用而非逐个生成的核心理由：只有同一上下文才能保证入口到深处的叙事递进与呼应。

**Step 3 — 怪物生成**。所有 `(场景, 角色序号)` 对展开为并发 LLM 调用。角色间无依赖，并发将总耗时压缩至最长单次调用。单角色失败只丢弃该角色，所有角色均失败才丢弃场景。

**Step 4 — 实体组装**。零 LLM 调用，纯确定性映射。`DungeonBlueprint` 转为 ECS 实体树（`Dungeon` → `CombatRoom` → Stage + Actor）。当前为所有怪物统一赋予「纯攻击型」战斗关键词——这是框架层的行为预设，与故事内容无关。

Step 5（场景插画）已实现但未接入主管道，不阻塞副本基础可用性。

---

## 设计决策

| 决策 | 理由 |
| --- | --- |
| 场景数量与角色数由 LLM 决定 | 硬编码会使不同规模的副本产出单一 |
| Step 2 一次性生成全部场景 | 场景间的递进关系需要同一上下文 |
| Step 3 并发调用 | 角色间无依赖，纯性能优化 |
| 中间文件逐步骤落盘 | 支持断点恢复与人工调试 |
| Step 4 零 LLM 调用 | 组装是纯结构映射，无需创意决策 |
