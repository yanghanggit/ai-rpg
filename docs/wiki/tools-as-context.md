# 工具即上下文（Tools as Context）

---

## 核心命题

Agent 一次请求发给模型的内容，不只是任务提示词：全部工具的 `name`、`description` 与 `parameters`（JSON schema）同样随请求进入上下文窗口。它们共同决定模型看到什么、能做什么、被什么约束。因此工具不是「给代码看的接口」，而是「给模型看的任务契约」——必须按提示词的标准来设计。

## 为什么必须这样看

- **token 是共享预算**：工具 schema 每轮随请求发送；提示词里重复同一约束，等于为同一笔信息付两份开销。
- **注意力会被重复稀释**：同一约束出现在两处，一旦措辞不完全一致，模型就要自行裁决，遵循率随之下降。
- **单一事实源**：一条约束写两处，改动必然漂移；写一处，改一处即全局生效。

## 分工原则

- **「能不能」交给 `parameters`**：类型、枚举、范围、必填、数量上限、格式等可由 schema 直接强制的硬约束，放进参数定义，不用自然语言在提示词里复述。
- **「为什么 / 边界」交给 `description`**：schema 表达不了的负面约束、跨字段语义、能力边界，写进工具描述——模型同样会读到。
- **「对象专属方向」交给数据本身**：每个候选对象各自的引导说明随该对象下发（自描述数据），取代所有对象共享的一份全局规范。
- **「任务与叙事」留给提示词**：提示词只保留本次任务、上下文输入（如投入材料）与叙事约束，不重复字段语义与格式。
- **「计算端持有」的东西不进上下文**：内部标识不应让模型搬运；改用计算端可解析的编号（句柄），减少幻觉与无谓复制。

## 工具名与调用序列也是提示

- 命名要传达语义与复用边界：通用动作不要绑定具体场景，否则复用时要被迫改名，且让模型误以为它只服务某个场景。
- 一组工具本身编码了工作流（浏览 → 精读 → 选型 → 提交 → 收尾）。用工具序列表达流程，比在提示词里逐条写「第一步 / 第二步」更稳、更省。

## 全局规范与自描述数据

两者都是上下文，取舍看的不是「哪种更短」，而是「哪种让模型更难错」：

- 规则对所有对象一致、对象多、同一请求内重复次数高时，全局规范只发一次更省。
- 每个对象的引导方向不同，或对象少（同一请求内重复次数有限）时，把说明放在对象上更精确，避免模型把某对象的说明误套到另一对象。

## 反模式

- 同一约束既写在提示词、又写在 schema：两处维护、两处漂移。
- 用一段全局规范覆盖所有对象，迫使模型在对象之间做本不该由它做的映射。
- 让模型用内部标识定位对象，导致复制错误或凭空编造标识。
- 工具名携带场景词，复用即被迫重命名。
- 在提示词里重述字段语义、格式与数量限制——这些本可由 schema 或对象说明承担。

## 优化既有提示词的检查顺序

1. 逐条问：这条指令能否由 schema 强制？能则移入 `parameters`。
2. 不能由 schema 强制的语义 / 边界：移入工具 `description` 或对象自身说明。
3. 仍是任务 / 上下文 / 叙事：留在提示词。
4. 查重复：同一事实是否在多处出现？只保留最合适的一处。
5. 查命名：工具名 / 参数名是否语义清晰、可复用、不泄漏场景。
6. 查泄漏：是否要求模型搬运本可由计算端持有的内部标识？
7. 回归验证：复跑端到端，观察非法提交率、重试次数与上下文规模的变化。

## 度量与目标

记录提示词与工具 schema 的体量变化，以及端到端运行中非法提交、重试、未结算效果的次数。目标是「同样的输出质量下，更少的重复与更低的上下文占用」，不是单纯把提示词压短。

## 结论

把「是什么 / 能不能」交给 schema，把「为什么 / 边界」交给 `description`，把「对象专属方向」交给数据本身，把「任务与叙事」留给提示词，并让工具名与调用序列承担流程表达——这就是「工具即上下文」的落地方式。
