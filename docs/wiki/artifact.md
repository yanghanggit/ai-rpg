# 神器（Artifact）

---

## 定位

神器是内容作者书写的**场景级战斗修正规则**载体，同时是世界的**第一公民实体**：它不进背包、不进牌堆、不物化为卡牌，而像角色与场景一样拥有全名、人设（`system_message`）与可挂载组件，可在运行点被作为独立 agent 唤醒。

## 构成与挂载

神器实体由工厂（`create_artifact`）生成，其系统提示词由战役设定、全局规则、神器人设（profile）与修正规则（modifiers）共同构成——修正规则以自然语言列表落入人设，供神器 agent 在运行时自行解释，内容作者不接触引擎视角。

归属关系由 `ReliquaryComponent` 声明：场景或角色携带该组件，列出其名下神器。管道中的神器实体初始化系统（幂等）把每个神器物化为独立实体，并在 `ArtifactComponent` 上承载神器完整定义与持有者实体全名（`holder`，作用类似 `ActorComponent.current_stage`），使「谁持有神器」成为可检索的一等关系。

运行点由标记组件表达：挂 `PostArbitrationComponent` 表示该神器在出牌/消耗品仲裁之后运行。新增运行点时，只需定义新的标记组件与对应系统，既有神器数据不必改动。

## 仲裁时如何生效

出牌/消耗品仲裁由各自系统先完成一次结算。随后 `ArtifactPostArbitrationSystem` 响应 `PlayCardsAction` / `UseConsumableItemAction`，收敛作用域——只取持有者为当前战斗舞台或本场存活角色的神器——逐一**以神器实体自身**为 agent：

1. 注入当前回合数、神器身份与持有者、场上存活阵营；
2. agent 依自身人设中的修正规则判定是否触发（如「第 2 回合」）并调用 `set_entity_hp` 覆盖式写入最终 HP；
3. 提交仲裁结果（战斗日志/叙事），落库并广播。

多个神器按实体创建顺序依次结算，后者可读到前者已落库的 HP。

> 记忆去向：神器作为 agent 会把每次结算（prompt、工具轨迹、结果）写入**自身持久记忆**；同时把「发生了什么」写入场景实体记忆，并通过事件广播使场景与场上角色均获得记忆。

> 权限边界：神器 agent 不是场景本身，不读也不写场景环境快照（`EnvironmentComponent`）。它对环境的认知只来自被广播与写入记忆的事件，由后续推理自行维护。

因此「第 N 回合队伍方全员倒下」「怪物伤害翻倍」这类场景规则以内容数据存在，不改引擎。

## 设计意图

- 机制与内容分离：场景规则是数据，不是硬编码进仲裁系统的分支；运行点用标记组件表达，可扩展。
- 神器即实体：神器携带自身人设，被唤醒时以自己的视角解释规则，而非借道一个通用的「神器仲裁者」，使规则、归属与身份三者合一。
- 借重 LLM 的灵活性：规则由临时 agent 在运行时按需发现并解释，而非系统预先筛选注入，保留内容表达的空间。
- 场景级而非卡牌级：神器规则对该场景内所有出牌/消耗品仲裁生效，是背景约束；卡牌词缀则属于单次出牌/受击结算。
