# 战斗管道（Combat Pipeline）

---

## 定位

战斗是一个以 `Combat` 状态机为核心的回合推进过程，由 ECS 处理器链按注册顺序驱动——顺序即因果链，无事件总线、无中心化状态机。战斗房间只是战斗的载体：它提供战场环境（stage）与参战角色（actors）；战斗本身是独立于房间的生命周期——**初始化 → 多回合累积推进（直到分出胜负）→ 结束**。

## 三阶段框架

### 初始化（仅一次）

把预置牌库确定性填入抽牌堆，为参战角色挂载空牌堆并注入战场环境，随后切换到进行中。卡牌在此第一次被获取：从 `DeckComponent` 进入 `DrawPileComponent`（按角色攻击/防御对伤害与格挡做叠加），尚未进手。

### 回合推进（循环，直到结果）

每回合内部是一条固定因果链：抽牌 → 出牌决策 → 动作执行 → 仲裁 → 死亡判定 → 回合完成 → 清理 → 胜负判定 → 下一回合。其中每个角色 pass turn 时的仲裁顺序为：出牌/受击仲裁 → 回合结束词缀 → 自主运行词缀。链由 `process()` 心跳驱动——系统按注册顺序执行、各自检查状态决定是否行动。胜负判定是唯一退出分支。

抽牌是回合的唯一入口：`DrawCardsAction` 触发时先创建新回合（无回合或上一回合已完成时），再完成全员抽牌，二者在同一处理周期内连续完成，一个回合每个存活参与者只抽一次。回合内出牌等行动均以抽牌完成为前置。抽牌是卡牌第二次被获取的时机：从 `DrawPileComponent` 进入 `HandComponent`（先取回保留牌，再尽量抓满目标张数；保留牌不占抓牌名额）。回合内装备物化、可传递牌转移也会改变手牌。

### 结束（仅一次）

掉落、战斗摘要归档、三堆牌副本清空、装备归还；`DeckComponent` 原始牌库完整保留。

## 回合（Round）与行动（turn）

`Round` 快照承载一个回合的推进状态，三个字段构成「行动权推进」机制：

- `action_order`：回合开始确定的行动顺序快照（按角色有效速度降序，速度相同按实体创建顺序升序；有效速度 = 基础 `speed` + 已装备件 `speed` 之和；本回合内不变），决定「谁先行动」。
- `current_actor`：当前应行动的角色，由「`action_order` 中第一个未过牌且未死亡」推导，是派生指针，不是独立状态。
- `completed_actors`：已过牌的角色列表，是行动权推进的唯一依据。

回合内的最小单位是**行动（turn）**：轮到某角色时，它可连续出牌、用消耗品、物化装备，直到它**过牌（pass turn）**。过牌是角色级动作——把该角色记入 `completed_actors`、把 `current_actor` 推进到下一位，只结束「这一个角色的行动窗口」。

## 过牌与回合结束是两个粒度

**过牌（pass turn）≠ 回合结束**：过牌只结束单个角色的行动窗口；当且仅当所有存活角色都已过牌，回合才完成，随后清理旧手牌、创建下一回合。能量耗尽只限制能打出的牌数，不自动过牌。

`on_turn_end_affixes`（回合结束词缀）结算于**持卡人每次 pass turn**，且**效果目标恒为当前持卡人本人**（原始持有者或被传递后的持有者），而非整回合结束——「回合结束」在此指「该持有者自己的行动窗口结束」，与「所有存活角色都过牌」是两个粒度。`on_autonomous_affixes`（自主运行词缀）在同一 pass turn、回合结束词缀**之后**结算，但**效果目标为场上任意存活角色**，不锁定持有者。

→ 参见：[卡牌数据模型（Card）](card.md)、[手牌（HandComponent）](hand.md)

## 设计决策

### 牌库预置，抽牌堆确定性填充

初始牌库由角色蓝图预置卡牌直接写入 `DeckComponent`，战斗起始不调用 LLM；抽牌堆按角色攻击/防御对伤害与格挡做叠加后确定性填充。意图：牌库内容回归内容作者的确定性控制；属性叠加使同一张预置牌在不同角色身上呈现差异化强度。

### 仲裁的归属

仲裁按触发时机归属不同主体，而非统一由场景实体处理：

- 出牌仲裁由场景实体执行：它持有战场环境叙事与各角色 HP 变化通知，能产出叙事一致的结果；叙事只影响演出措辞，伤害仍按确定性规则结算。场景实体的环境快照已在战斗开始时注入其上下文（`CombatInitStageSystem`），战斗中的仲裁不再读写该组件。
- 回合结束词缀仲裁由**所在场景**执行（与出牌仲裁同一仲裁者），结算触发 pass turn 的持卡人手牌中带回合结束词缀的牌，结果写入场景记忆并**全场景广播**。词缀是持有者自身的持续状态，但结算视角与叙事一致性由场景统一承担。
- 自主运行词缀仲裁同样由**所在场景**执行，紧接着回合结束仲裁之后、以同一 pass turn 触发：结算持卡人手牌中带 `on_autonomous_affixes` 的牌。与回合结束词缀的关键区别是**效果目标为场上任意存活角色**（不锁定持有者），卡牌作为自主主体可影响全场；其造成的伤害同样算「命中」，会触发被命中者的受击词缀。
- 消耗品不单独仲裁：使用消耗品只是把它的内置卡牌物化进手牌（见 `UseConsumableItemActionSystem`），真正的效果结算与其他手牌一样，由场景实体在出牌仲裁中完成。
- 神器仲裁由场景实体作为仲裁者执行：神器与 `Card` 同级，是场景级战斗修正规则的载体，被 `ReliquaryComponent` 携带、且 `phases` 命中 `ArtifactPhase.POST_ARBITRATION` 的神器，会在出牌仲裁后由所在场景结算；结算过程写入场景持久记忆，并通过广播使场上角色获得记忆。

四种仲裁（出牌 / 回合结束 / 自主运行 / 神器）的上下文处置一致：成功则把整段推理轨迹压成一条总结写入场景记忆，未完成则原样保留轨迹并补一条失败说明、同时在回合日志记一条失败条目。这些记忆只存在于地下城场景实体上，退出副本时随场景实体（经同一出口统一销毁）一并消失。

→ 参见：[上下文窗口管理（Context Window Management）](context-window-management.md)

> 环境快照：`EnvironmentComponent` 仅在初始化时由 `EnvironmentInitializationSystem` 写入一次。战斗中的各仲裁者（场景/神器、持卡人）均**不读不写**该快照；它们只把「发生了什么」写入相关实体记忆，由各自后续推理依上下文维护对环境状态的认知。

→ 参见：[卡牌数据模型（Card）](card.md)、[消耗品系统（ConsumableItem）](consumable-item.md)、[神器（Artifact）](artifact.md)

### 多值文本字段逐条结算

卡牌四词缀（`on_play_affixes` / `on_hit_affixes` / `on_turn_end_affixes` / `on_autonomous_affixes`）与神器 `modifiers` 都是**多值列表**：每个元素是一条完整、独立的规则。生成与填充侧统一清洗（去首尾空白、丢弃空项、按序去重），消费侧逐条分行注入并**逐条全部结算**——出牌、回合结束、自主运行、怪物决策按词缀逐条渲染；禁止用 `、` 之类的连接符把多条独立条目合并成一个整段字符串。

### 状态就是牌：没有独立状态存储

系统没有 buff / 标记组件，也无法通过仲裁器写除 `HP` 以外的状态：一个角色当前的「状态」= 其手牌中承载词缀的牌。给对方施加持续状态靠 `transferable`（副本进对方手牌，保留原 `source`；副本落地即 `transferable=False`，只传一跳，持有者不能再次转手），由该牌自带的 `on_hit_affixes` / `on_turn_end_affixes` 结算；出牌仲裁的 `get_entity_stats` 会把目标手牌中带 `on_hit_affixes` 的牌一次返回，作为可读状态面。**结构性效果**（抽牌 / 弃牌 / 移牌 / 能量 / 额外行动 / 改流转 flag）不在原语范围内，属骨架字段与数据流转系统；词缀若声明这类效果或凭空标记，不会被结算，会被仲裁器记入 `unsettled_affixes` 供 telemetry。

### 解释不了的词缀：让生成 agent 在提交前知道

「这条词缀能不能被解释」必须由**生成 agent 在提交前**判断：只有它握着完整上下文（词缀槽 + 结算原语 + 想表达的效果）。事后没人能补——牌库打磨结构上禁止改属性 / 词缀，仲裁时生成 agent 早已不存在。生成契约（`card_common` 引擎的 `submit_card` 工具 schema，「结算原语」硬边界 + 范围外禁止，见[卡牌设计指南（Card Design）](card-design.md) 的「生成契约」）与 `validate_affix_slot`（只守格式硬不变量）就是这条分工。

`unsettled_affixes` 是**万一漏过时的兜底**，不是交接点：

- 它会将提交结果写进场景记忆（`.worlds/<user>/<game>/<ts>/memories/场景.*.jsonl`）并打一条 `logger.warning`；
- 但它**没有自动接收者**：生成 agent 在仲裁时已消失，牌又不能承载回执（打磨只允许改 `name` / `description`）；
- 所以把它当开发遥测去读日志 = 把静默失败留给开发者，正是本项目要消灭的失败模式。

排查命令（字段嵌在被转义的 JSON 字符串里，故模式需带 `\\"`）：

```bash
grep -rho 'unsettled_affixes\\": \[[^]]*\]' .worlds --include='*.jsonl' | grep -v '\[\]'
```

> 观测记录：截至当前全部存档（3003 个记忆文件、89 条仲裁提交），非空 **0 条**、日志 warning **0 条**——与「生成期自检有效」一致。

### 仲裁数值来源唯一性

仲裁结算的数值以系统给出的角色状态为唯一来源：**总格挡**（角色级＝其手牌 `block` 之和）已聚合完成，LLM 必须直接采用，不得再叠加单牌 `block`，也不得从对话历史或前几回合广播中补算卡牌与数值。该约束用于阻断 LLM 把历史回合出现过、当前并不持有的卡牌误植回本次结算，也用于区分「总格挡」（角色级）与「单牌格挡」（`block` 字段）。

### 结算：LLM 判系数，代码算数值

出牌仲裁与回合结束仲裁共用同一套**计算骨架**，且**算术完全由代码完成**（`systems/arbitration_calculator.py` 的纯函数，带单测）：

- 承伤（过格挡）：`每击伤害 = max(0, base_damage × 伤害系数 − 目标总格挡 × 格挡系数)`，逐击求和；
- 受效（反伤 / 吸血 / 治疗，不过格挡）：`各分量 = 四舍五入(base × 对应系数)`，`净扣减 = (反伤 − 吸血 − 治疗) × hit_count`。

LLM 只做三件事：为每条效果选定 **base**、判定**系数取值**、并**写出依据**。它通过两个工具提交判断：

- `resolve_damage(entity, base_damage, hits, damage_mult, block_mult, rationale)` —— 出牌仲裁为每个承伤目标一次；回合结束仲裁目标恒为持有者，故对持有者一次；
- `resolve_effect(entity, base, hits, reflect_mult, lifesteal_mult, heal_mult, rationale)` —— 出牌仲裁为每个受效角色一次；回合结束仲裁目标恒为持有者。

系数的默认值分别为 伤害 1 / 格挡 1 / 反伤 0 / 吸血 0 / 治疗 0，全部由 `on_play_affixes` / `on_hit_affixes` / `on_turn_end_affixes` / `on_autonomous_affixes` / 神器 `modifiers` 的自由文本指导取值。`base` / `base_damage` 是 affix 引用的那个数值（通常取本卡 `damage` / `block` 字段，或文案明示的数字）——系统不解释字段语义，由 LLM 依文案判断它代表什么（如 `旧疤结痂` 用 `block` 当伤害基础）。伤害系数可用于语义条件上调（如「对动物属性 +50%」→ 1.5、「目标带某标记时×2」→ 2），此时 LLM 结合对手外观 / 人设等已知信息自行取值。反伤 / 吸血 / 治疗一律**按每击**（代码负责 ×hit_count），暂不支持「一次性」单发标记。

`resolve_effect` 在**出牌仲裁**中不限阵营与身份（名称为「受效角色」）：「治疗友方」「对任意角色施加反伤 / 吸血」都是显式路径，具体由卡牌选择决定；若一条效果引用两个不同来源（如反伤取目标 `block`、治疗取本卡 `damage`），拆成两次 `resolve_effect` 调用即可，会自然累积。**回合结束仲裁例外**：其目标恒为当前持有者本人，不得指向其他角色。

> 设计取舍：工具里只允许出现**通用数值系数**，即编码的是「算术」而非「词缀语义」——不为具体牌名 / 词缀名在代码里分支（例如不引入 per-affix 的 `bypass_block` 标志），也不允许骨架表达不了的机制硬塞，这类词缀原文进 `unsettled_affixes`（仅供 telemetry，不结算）。语义裁决权完全留在 LLM，算术确定性交给代码，符合「LLM 扮演 DM、系统当规则书」的定位。

### 过程留痕：日志由系统生成

`combat_log` **不再由 LLM 撰写**：每次 `resolve_damage` / `resolve_effect` 调用时，代码把刚算出的数值渲染成一段日志（含代入式与 `旧→新`）并累积；`submit_arbitration` 后按顺序拼成完整 `combat_log`。LLM 在 `rationale` 字段里的依据会附在对应段落括号内。格式：

- 承伤：`[出牌者|卡牌→目标: D×伤害系数kd − B×格挡系数kb = 每击h × hits击 = Z（依据）] HP:目标 旧→新`
- 受效：`[角色: 反伤base×mult=v/击 ×hits击=T … = 净扣减/回复Δ（依据）] HP:角色 旧→新`

由于**同一段代码既算数值又生成日志**，「过程」与「结果」在构造上不可能对不上——这是相对早期「LLM 心算并写日志」的根本改进。`submit_arbitration` 的 `combat_log` 入参保留（三份同名工具 schema 必须一致，见 `test_arbitration_submit_tool.py`），但本仲裁侧忽略其内容。**数值仍不加护栏**：系数判错不会被拦截，但每次判错都会连同依据完整留痕，可事后核对与回报。

### 观测记录：骨架消歧

同一快照（`基础攻击` 打持有 `[护喉]` 受击词缀的头狼）在引入骨架前后的对比：

- **修骨架前**：模型在「受击词缀伤害是否过总格挡」上反复摇摆（同一 reasoning 内自相矛盾多次），同一输入两次运行结果不一致。
- **修骨架后**：直接按骨架判定 `护喉 = 反伤 2`，写出 `反伤2/击 ×1击=2`，结果稳定、可核对。

根因：旧措辞「词缀追加的伤害不过总格挡」把一条**通用规则**塞进了 DM 临场裁定，导致歧义；改为全局骨架后，规则由系统定死、参数仍由词缀给，歧义消失。

> 此处不再保留旧版「基础段 / 词缀段」与「约 10%–15% 残留」的记录——那套措辞已被全局骨架取代。

### 决策与结算分离

出牌分决策与仲裁两步：决策并行（各行动者同时选牌选目标），仲裁单线程（叙事一致），决策 LLM 不受仲裁风格干扰。怪物决策由 `MonsterPrePlaySystem` 用角色自身记忆完成，`PartyPrePlaySystem` 与怪物侧对齐结构。

一次怪物行动只产出一张牌决策（选一张牌或过牌），不存在连打多张。怪物决策采用「提示词预防 + 决策兜底」双层防护：只暴露费用可支付的牌并引导能量不足时过牌；即便选错，也在生成出牌动作前拦截、强制过牌，保证错误决策不进入结算。

怪物决策的对手视图遵循「模糊总量 + 相关点亮」：每个对手只暴露 `HP`、`总格挡`（手牌 `block` 之和，持有即生效）与 `手牌总数`（一个整数），并在此总数中点亮两类牌——带受击词缀（`on_hit_affixes`）的牌，或来源为本怪物（`source` 等于怪物名）的牌。前者让怪物权衡「命中该对手会触发什么反制」，后者让怪物看到自己投递进对手手牌的牌（配合 `transferable` 副本保留原 `source`、且落地即失去传递性反噬）。其余手牌保持隐藏。

### 角色侧 LLM 的留痕策略

战斗中与 actor 记忆相关的写入只有下列几类，策略统一为「推理留痕 / 告知结果 / 零接触」：

- `MonsterPrePlaySystem`（出牌决策）与 `CombatLootSystem`（战利品推断）：**全部留痕**——human 写请求原文（带 `draw_cards_round_number` / `combat_loot_reasoning` 标记），ai 写回包原文；失败无回包时只留请求侧，不伪造 AI 回复。于是「怪物在战斗中为主体的推理」在记忆里完整可对账。
- `ContextCompactionSystem`（上下文压缩）：超阈值的 agent（含 actor）记忆被换成一条摘要，这是唯一会改写 actor 记忆本身的系统级 LLM。
- 胜负通知（`combat_outcome`）发给**全部参战者**（含怪物），文本按各自阵营视角生成：队伍看 `CombatResult`，怪物看其反面。故怪物记忆里也有「这场战斗我输了」这一条终局陈述（此前只有「HP 归零」）。
- 玩家侧的数据变化同样留一条**自我状态说明**（只写给本人，不广播）：`CombatLootSystem` 写「# 你的战利品」（`combat_loot_items`），`PickSpoilsActionSystem` 写「# 你收下了战利品」（`spoils_pick`），使 `LootComponent` 写入与 `SpoilsComponent → DeckComponent` 的追加都能在记忆里对账。
- 外观合成**不在此列**：它由世界实体「世界.外观合成」以「system prompt + 任务提示词」一次性完成，不读任何 agent 记忆、也不留推理原文；结果只落 `AppearanceComponent`，并给本人补一条自我状态说明（`# 你的外观 …`，不广播）——外观变化事件的广播属于穿装动作（见[战役设定与系统提示词的分层](campaign-setting-rules-bridge.md)）。

仲裁类（出牌 / 回合结束 / 自主运行 / 神器）的主体是场景实体而非 actor，结果只写场景记忆；场景实体在退出副本时统一销毁，记忆随之消失。

一条边界说明：这四种仲裁走 `agent_loop`，其「请求 → 工具调用 → 提交」的原始轨迹是**直写进记忆**的（不经过 `add_human_message` / `add_ai_message` 的标记校验），结算成功后由 `loop_id` 把整段压成一条摘要 + 数据日志，`replaced_messages` 留存原文。走同一路径的还有副本生成的三个步骤、家园 NPC 计划、插图与卡牌设计——它们属场景 / 世界实体侧，不在「角色侧留痕」的范围内。标记体系统一只约束经 `add_*` 写入的消息；直写路径由**存档前的兜底闸门**保证不写入未登记标记。

广播的**自我回显**口径统一为：行动类广播在发起者另有更精确的自我记录时排除发起者（出牌有 `play_card_record`）；观察类广播保留发起者（过牌、装备/消耗品物化、说话、外观更新、仲裁结果），因为这些是发起者对该事件的唯一凭据。

→ 对账工具：[`scripts/inspect_memory.py`](run-agent-game.md)（`--diff` 直接给出记忆增量与各牌堆差分）
