# 卡牌数据模型（Card）

---

## 定位

`Card` 是战斗行动的最小单元。其字段按「谁来消费」分为三层：确定性骨架、语义词缀、生命周期流转。三层职责正交，共同决定一张牌在战斗中的行为。

---

## 确定性骨架（计算端消费）

`name` / `description` / `cost` / `damage` / `hit_count` / `block` / `target_type` 构成牌的确定性底座。

`cost` 由出牌执行端扣减 energy；`damage` 与 `block` 在牌进入战斗牌堆时叠加角色攻击/防御，之后分别参与伤害结算与持有期防御；`target_type` 决定目标解析策略——单个目标、阵营锚点展开、阵营散射、锁定自身四种语义。

`name` 是标识与 LLM 决策的匹配键；`description` 是叙事锚点，只影响仲裁叙事演出，不改变确定性数值结算。

---

## 语义词缀（LLM 仲裁消费）

五组词缀 `on_play_affixes` / `on_hit_affixes` / `on_turn_end_affixes` / `on_autonomous_affixes` / `engine_affixes` 是自由文本 `[词缀名]:机械结算描述`，分别锚定出牌、被命中、回合结束、自主运行、运转（牌堆层面）五个触发时机。词缀由仲裁 LLM 结合牌面数值与场景状态解释执行，是玩法灵活性的主要来源。

词缀名是风味层，可自由个人化；机械结算描述是规则层，是仲裁执行的权威依据。

**一个列表元素只装一条单行规则。** 多值列表的语义是「多条独立规则各自结算」，不是「一条长文本」：把两条规则拼进一个元素（或用换行塞进去）会让仲裁漏结算，所以这是模型层硬约束；叙事与心理描写不写进词缀文本，那是 `description` 的职责，种子数据侧另有清单式校验。

词缀的格式与约束随生成契约的 `submit_card` 工具 schema 下发，每个原型的引导方向见其 `design` 字段（结算原语边界、数值限制、书写约定、非法置空等见[卡牌设计指南（Card Design）](card-design.md) 的「生成契约」），本文不重复。

模型层没有独立的状态 / buff 组件：一个角色的「状态」即其手牌中承载词缀的牌。持续状态因此必须由牌本身承载（设计方法见 [卡牌设计指南（Card Design）](card-design.md)）。

结算归属：出牌与受击并入出牌仲裁；回合结束词缀由独立仲裁结算，在持卡人每次 pass turn 时触发，只结算其自身手牌中带该词缀的牌，跨回合保留即持续触发；自主运行词缀在回合结束词缀**之后**、由同一仲裁者在持卡人每次 pass turn 时结算——它与前三者的根本区别是**效果目标为场上任意存活角色**（不锁定持有者），卡牌由此成为可影响全场的自主主体（召唤兽 / 图腾 / 光环 / 持续诅咒等）。

运转词缀是唯一**不结算 HP**的一类：它在出牌结算完毕之后触发，作用对象是牌本身在牌堆里的存在方式——复制、移动、改写字段，因此改的是「这张牌之后怎么活」，而不是「这一击打掉多少血」。它的仲裁者不是场景，而是牌的持有者本人：他拿到一组操作自己容器（手牌 / 抽牌堆 / 弃牌堆 / 消耗堆）的工具，由词缀文本决定怎么用。类别由槽位决定，词缀名与其他槽一样写风味名；文本只写规则，不写故事与心理（叙事归 `description`）。

→ 参见：[战斗管道（Combat Pipeline）](combat-pipeline.md)（仲裁与词缀结算时机）

## 生命周期流转（计算端消费）

`playable` / `exhaust` / `retain` / `ethereal` / `transferable` 控制牌在牌堆间的确定性流转，每个标志单一职责：

- `playable`：不可出时在出牌执行端拦截。
- `exhaust`：出牌后永久离场，不进弃牌循环。
- `retain`：回合末保留，跨回合存续。
- `ethereal`：pass turn 时若仍在手牌则自动离场。
- `transferable`：出牌时**额外**按命中分配投递副本（副本落地即 `transferable=False`、**只传一跳**，收到副本者不能再次转手；本体照常结算并进入弃牌/消耗流程）。目标经 `target_type` 解析，可显式选择自身或直接使用 `target_type=SELF`（锁定自身、无需传入目标）实现「自传递复制」（拿回的副本同样不可再传）。副本数 = 该角色在解析目标列表中的**出现次数**：`SPREAD` 的列表就是命中分配（一击一项、每次命中独立随机落到阵营存活角色上，可重复、也可能有人一次都没中），因此 5 击散射全落在同一名角色身上就投 5 份副本、分散开来就各拿几份；`SINGLE` / `ALL` / `SELF` 的列表里每名角色各一项，故各拿一份（`SINGLE` 的 `hit_count>1` 是多段伤害，不产生额外副本）。

组合这些标志即可表达「一次性爆发」「常驻被动」「转嫁型持续效果」等玩法。但并非任意组合都成立——其互斥与依赖是硬约束。

→ 参见：[卡牌设计指南（Card Design）](card-design.md)（布尔字段的互斥与依赖）

## 牌堆变更对谁可见

判据是「**谁的容器动了**」，而不是「谁触发的动作」：牌库、待领取、抽牌堆、手牌、弃牌堆、消耗堆（含抽牌堆里的保留队列）任一处发生变更，就写一条只给容器主人的说明。于是自己抽牌会收到记录，别人打出 `transferable` 牌把副本塞进我的手牌**同样**会收到——我的容器被改了，纸面上那个人出的是什么牌与我无关。

决策与事实分层记录，互不替代：出牌是决策（决策层只写「打了什么、为什么」），牌最终落在弃牌堆还是消耗堆是事实（容器层照实记一条）。唯一的例外是消耗牌——它不会停在弃牌堆，因此弃牌堆那条不写，由消耗堆那条说明去向，避免同一次出牌出现两条自相矛盾的事实。

真正重复的才去重：收到副本的卡牌摘要、领取奖励的领取记录、装备与消耗品物化的行动广播——它们本身已经是容器事实，容器层不再另写。

队列增减本身是私人信息，因此这类记录只写给本人，从不广播；「某人打出了什么」仍然照常广播。

→ 参见：[战斗管道（Combat Pipeline）](combat-pipeline.md)

## 来源引用（source）

`source` 记录牌来源（生成/注入者）的名称：预置牌为角色自身，装备物化牌为发起行动者。它有双重身份——既是追溯手段，也参与玩法语义：词缀可用 `source 者`（持有者 == `source`）与 `非 source 者`（持有者 ≠ `source`）按持有者与来源的关系设生效条件，仲裁 LLM 据此判定是否结算；配合 `transferable`（副本保留原 `source`，但落地即 `transferable=False`）即实现「投掷给敌人后反噬对方、且原主重抽不自伤」的转嫁机制——只转嫁一跳。

装备物化牌的归还回链改由装备侧的登记组件在战斗结束后统一处理。

→ 参见：[装备系统（GearItem）](gear-item.md)

## 设计决策

分层的核心是「确定性骨架 + LLM 语义」：计算端只保留让回合循环可运转的最小确定性（目标、流转、能量、死亡），词缀解释与数值结算交给 LLM。这是游戏场景下的刻意取舍——接受偶尔的数值/语义偏差，以换取玩法灵活与低脚手架成本。

对生成侧（候选奖励、牌库、工坊合成）而言，功能字段的提交边界由生成契约统一约束（`submit_card` 工具 schema，见[卡牌设计指南（Card Design）](card-design.md) 的「生成契约」），`name`/`description` 由生成方提供、不进入该约束——契约只描述「牌能做什么」，不描述「牌是什么」。
