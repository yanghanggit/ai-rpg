# 战役设定与全局规则（CAMPAIGN_SETTING / SYSTEM_RULES）

## 分层

世界知识分两层注入每个实体的 system prompt，二者都封存在 `demo/`（故事层），引擎保持内容无关：

- `SYSTEM_RULES`：全局规则，是所有实体共同遵守的规则。它不是一块铁板，而是**游戏无关规则 + 扩展内容**的组合：
  - **游戏无关规则**：游戏机制的通用骨架——角色扮演契约、游戏实体、实体全名、根属性、战斗机制、场景移动、扮演与事实，与任何具体故事内容无关。
  - **扩展内容**：定义"对于特定故事内容，什么可以被称作一个副本、一场战斗，以及各类物品是什么"这类内容相关的规则语义，随故事而变。同一概念在不同故事主题下承载不同语义——副本可以是坠入的一场梦，也可以是一处地理位置或一场战役。当前注入的扩展内容为 `DUNGEON_RULES`（副本语义）；物品语义映射（原 `ITEM_RULES`）已暂时移除。
- `CAMPAIGN_SETTING`：战役大背景（类型标签、世界结构、题材范围与转译约束），是全部实体的最低公共知识；不含具体地点、国家、势力与游戏流程。

`Blueprint` 以 `campaign_setting` 与 `system_rules` 两个字段承载这两个 prompt 层字段；工厂（create_actor / create_stage / create_world）与副本组装系统（AssembleDungeonSystem）都从蓝图取值，不再硬编码任何规则文本。

## 游戏无关规则与扩展内容

全局规则拆成两部分，是因为"副本""战斗"这类概念同时具备两种性质：

| 概念 | 游戏无关的部分 | 内容相关的部分（扩展内容） |
| --- | --- | --- |
| 副本 | 由多个顺序房间构成，每间对应一处场景与特定挑战 | 副本的语义（一场梦 / 一处战场 / 一座地宫……） |
| 战斗 | 回合制、无位置与命中、效果必定生效 | 战斗发生的层面与语义 |
| 卡牌/装备/消耗品/时装 | Card 是唯一效果载体、数值字段、词缀/格挡机制 | 物品的语义（符纸与短刃 / 程序与 ICE / 义体外装） |

- **游戏无关部分**属于游戏骨架，跨故事稳定，不应被故事语义污染。
- **扩展内容**是故事层对通用概念的具体化定义，随故事换皮。

组合原则：换故事时，只替换扩展内容，游戏无关规则保持不动。二者拼合后，才是最终注入每个实体的全局规则字段。

## 故事层两字段（Blueprint）

`Blueprint` 是引擎与故事之间唯一的注入边界，共承载两个故事层字段；引擎只按字段消费，不含任何具体故事文本。

| 字段 | 故事常量（demo/world.py） | 消费方 | 注入目标 |
| --- | --- | --- | --- |
| `campaign_setting` | `CAMPAIGN_SETTING` | 工厂（create_actor / create_stage / create_world）、AssembleDungeonSystem | 实体 system prompt 的「游戏设定」段 |
| `system_rules` | 游戏无关规则 + 扩展内容 | 同上 | 实体 system prompt 的「全局规则」段 |

字段默认值均为空串，旧 Blueprint / 存档未涉及引擎不认识的字段。

## system prompt 段序

实体 system prompt 统一按「内容在前、规则在后」排列，便于 agent 先建立设定、最后读到必须遵守的规则：

1. **游戏设定**（`campaign_setting`）——战役大背景，内容向；
2. **实体自身设定**——`角色设定`（`基础体型` 为其子标题）/ `场景设定` / `神器设定` + `神器修正规则`；世界实体则由 `role_rules` 自带段落承载；
3. **全局规则**（`system_rules`）——具有明确规则效果，置于末尾。

运行时的事件通知会把 agent 指回「游戏设定」与「全局规则」，本质是触发其对规则的回顾与遵守（见下文「事件级引用提示」）。

## 插图风格由世界实体承载

副本插图的画风、构图与负面词**不再进入 Blueprint**，而是由 `world_entities` 中的「世界.插图提示词」实体（`IllustrationComponent`）承载：其 `role_rules`（system prompt）定义视觉方向与提示词写作要求，Step 6 由该实体作为 agent 为封面与各房间编排文生图提示词。

引擎（`IllustrateDungeonSystem`）只传递事实（副本 / 场景 / 生物设定）与调用图像模型，不含任何具体画风或构图模板。换故事只改 `demo/world.py` 的该世界实体。

## 外观合成同样由世界实体承载

「基础体型 + 时装 → 当前外观」是纯文本改写任务，不属任何角色的叙事行为，因此同样交给世界实体：「世界.外观合成」（`AppearanceSynthesisComponent`）的 `role_rules` 携带书写规则（覆盖维度 / 以基础体型为底 / 禁止项 / 输出格式），任务提示词只剩数据（`base_body` + 时装名与描述）。

调用方只负责筛出待合成角色：管道起点补合成与穿装即时合成共用同一个世界实体与同一种请求形状——**只带该实体的 system prompt，不读也不写角色记忆**，结果只落在 `AppearanceComponent`。两者共用的部分单点维护，各自只保留触发时机与结果告知。

两条路径的“告知”刻意不对称：穿装是世界内发生的事件，由 `WearCostumeActionSystem` 广播「外观已更新」给全场景；管道起点的补齐属于数据修复（没有任何人记过旧外观），因此 `AppearanceSynthesisSystem` 只给本人补一条自我状态说明（`# 你的外观 …`），不广播。推理与告知由此彻底解耦。

请求的标识采用「主体|服务对象」形式，日志与对话转储能直接读出“这次推理是世界实体在替谁做”，回写时据此定位角色。

## 机制下沉与内容下沉的边界

系统提示词、任务提示词与工具 schema 三类载体职责不同，混淆就会把故事内容漏进引擎：

| 载体 | 允许承载 | 禁止承载 |
| --- | --- | --- |
| 故事层 system prompt（`demo/`） | 题材与世界观、审美边界、创作原则、字段的**内容**要求 | 引擎结构常量（房间数 / 怪物数等，由运行时按输入数据下发） |
| 运行时任务提示词（`systems/`） | 本步的输入数据（**含生成数量**）、工作流程、输出格式 | 题材与世界观（如「奇幻世界」「草药 / 矿物 / 兽材」） |
| 工具 schema（`ToolDefinition`） | 字段名、类型、枚举、字数区间、机械禁忌（不得出现数值 / 机制词汇） | 同上：任何故事语义 |

两条原则：

- **数量属输入数据，不属设定**：房间总数、每房间怪物数这类结构常量由代码持有，作为任务提示词输入下发（见[副本生成管道](dungeon-generation.md)），既不该写进 `demo/` 的 system prompt，也不该只留在 schema 里。
- **内容不上浮到运行时**：题材、物种谱系、材料意象等只存在于故事层。若运行时确需约束，只能以**回指**方式出现——例如时装合成的「命名和描述请复核『游戏设定』与你的自身设定」，把 LLM 指回自己的 system prompt，而不是在引擎里复述设定。

这条边界是单向的：`demo/` 的世界实体 system prompt **可以**引用引擎数据模型（`models/` 里的字段名、枚举与结构，如 `Card`、`hp / max_hp`、`opening / combat`），那只是「知道数据形状」，不算内容泄漏；被禁止的只有反方向——故事内容流进运行时任务提示词与工具 schema。同时注意避坑：即使允许，也不要在 `demo/` 里**复述**工具 schema 的规格（字数区间、字段级禁忌），那是同一约束两处维护，会漂移。

## 抽象设定是惰性知识

写进 system prompt 的故事语义属于惰性知识——LLM 就近采信事件通知文案，不会自发回读 system prompt 中远置的抽象设定（触发缺口）。

## 事件级引用提示

在副本生命周期通知（进入 / 推进 / 退出 / 撤退）中追加一句通用引用，把事件时刻的 LLM 指回自身 system prompt：关于副本及进出副本的设定，见你的「游戏设定」与「全局规则」。

该句不含故事专属内容，语义只存于全局规则与战役大背景（均在故事层），通知只负责触发回读。通知文案保持通用，引擎代码不被具体故事语义污染。
